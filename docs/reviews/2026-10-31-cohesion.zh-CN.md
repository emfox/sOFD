## 二、结构性错位（建议排期）

### 2.1 PDF 的文件结构知识分居两个 crate（[#37](https://github.com/emfox/sOFD/issues/37)）

门面自己拼 PDF 文档骨架：

- `sofd/src/export.rs:7` 导入 `lopdf::{Dictionary, Document, Object, ObjectId}`；
- `sofd/src/export.rs:18-40` 写 `/Pages`（Kids/Count/Parent）与 `/Catalog`（Pages/Root），再 `save_to`；
- 为此 `sofd/Cargo.toml:39,66` 让门面直接持有 `lopdf`。

而 convert 里已有同一份知识的单页版本：`sofd-convert/src/pdf/mod.rs:725-745` 在 `page_to_pdf` 里同样构造 `/Pages` 与 `/Catalog`。

**为什么是错配**：PDF 的文档骨架是**格式知识**，属于 PDF 后端；门面的职责是把多页排好序、合并统计、返回字节。现在门面为了补一个"多页"变体，把格式内部结构复制了一份，并额外背了一个 `lopdf` 直接依赖——门面越过了自己"只做编排"的边界。

**建议**：`sofd-convert::pdf` 增加 `pages_to_pdf(pages: &[&PageDisplay], options) -> Result<Vec<u8>>`（把现有单页版本的骨架逻辑参数化），门面只保留循环、`ConversionStats` 合并与 `ConversionOutcome`。随后 `sofd/Cargo.toml` 的 `lopdf` 与 `export.rs` 一起消失，`pdf` feature 简化为 `["convert", "sofd-convert/pdf"]`。

### 2.2 tauri 仍直接读 IR，`sofd::shell` 只完成一半（[#38](https://github.com/emfox/sOFD/issues/38)）

`sofd-tauri/src/wire.rs:12-14`：

```rust
use sofd_display::ops::{Color, LineCap, LineJoin, Paint, PaintRule, StrokeStyle};
use sofd_display::{DrawOp, ImageCodec, PageDisplay};
use sofd_render::{Shape, VectorPage};
```

因此 `sofd-tauri/Cargo.toml:30,31,35` 仍挂着 `sofd-display` / `sofd-render` / `sofd-geometry` 三条底层依赖。而门面已经 re-export 了 `Shape`/`VectorPage`（`sofd/src/lib.rs:47`），`sofd::shell` 的存在理由也正是"让 shell 不越层"（`sofd/src/shell.rs:1-6`）。

**为什么是错配**：这是 #32 没做完的部分。`shape_path_data` 把手伸进了 render，但序列化 draw op 需要的 `DrawOp`/`Paint`/`StrokeStyle`/`Affine` 还留在原地，于是 tauri 仍然一半走门面、一半走 IR。

**建议**：把 draw op 的**线格式**（witness 结构）收进 `sofd::shell`，或至少让 `shell` 重导出 `DrawOp`/`Paint`/`StrokeStyle`/`Affine` 四组类型；tauri 的依赖表因此收敛为 `sofd` + `sofd-session` + `sofd-icons`。这条做完，第二个 shell（#13）才有可照抄的样板。

### 2.3 convert 为一个 PNG 后端拖进整个栅格栈（[#39](https://github.com/emfox/sOFD/issues/39)）

`sofd-convert/Cargo.toml:22` 正常依赖 `sofd-render`，唯一使用点是 `sofd-convert/src/png.rs:8` 的 `render_page`。只想出 PDF/SVG 的构建（服务端批量转档正是这种）也要编 `tiny-skia` 一整套。

**建议**：`page_to_png`/`encode_png` 收进 `sofd-render` 的 `png` feature（它本就拥有 `RasterOutput`），convert 只保留矢量后端；或退一步，把 `sofd-render` 变成 convert 的 `png` feature 依赖。两种做法都能让 `--no-default-features --features pdf` 真正瘦下来。

### 2.4 下层 crate 的 benchmark 反向测上层（[#41](https://github.com/emfox/sOFD/issues/41)）

`sofd-parser/benches/memory.rs:6-8` 用 `sofd::Document`、`sofd_convert::png`、`sofd_render::RenderOptions`；`sofd-parser/Cargo.toml:28-32` 的 dev-dependencies 因此长期挂着门面与 convert。

这与 #36 修掉的 sofd-edit 测试同型（下层 crate 的测试去测上层集成），只是这次躲在 bench 里，所以审查上一轮没看到。

**建议**：`memory.rs` 移到 `sofd/benches/memory.rs`——它测的是"打开一份文档到出图"的全链路，本来就是门面的基准。移完 parser 的 dev-dependencies 只剩 testkit/proptest。

## 四、说法与事实不符的两处

### 4.1 theme 与 typography 互相矛盾（[#42](https://github.com/emfox/sOFD/issues/42)）

`sofd-egui/src/theme.rs:1-2` 声称自己是"the only place a colour or a point size is written"，紧接着第 6 行 `pub use sofd_session::typography::{BASE_POINTS, SCALE, Style}` —— 字号基数与八级比例其实定义在 `sofd-session/src/typography.rs:8-20`。

两处都不算错（比例确实 toolkit 无关，放在 session 可被第二个 shell 复用），错的是**两句话互相否认**。建议二选一：把 `typography` 提成与 `sofd-icons` 同级的共享小 crate（它现在的定位就是"第二个 shell 也照这个画"），或在 theme.rs 首行改成"颜色在这里写，字号比例在 session 的 typography"。

### 4.2 `sofd-bindings` 的名字暗示叶子，实际坐在门面之上

`sofd-bindings/Cargo.toml:14` 依赖 `sofd`（含 sign/search feature），因为 `search_hits(&Document)`、`signature_statuses(&Document)` 收的是门面的 `Document`。

一个叫"bindings"、描述为"plain data shapes"的 crate，方向却朝上：任何只想拿形状的消费者（比如将来的 Python 绑定、或只做 JSON schema 的工具）都得先把整座门面拉进来。

**建议**（不急于做）：形状与辅助函数分家——`DocumentInfo`/`SearchHitData`/`SignatureData` 保持零依赖，`search_hits`/`signature_statuses` 这类"从 `Document` 抽取"的函数留在门面或各 shell。这样 bindings 才能真正成为被复用的叶子。
